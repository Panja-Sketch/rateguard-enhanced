## D2 — IPIR v0.2 as a parallel module with a single lowering boundary

**Decision (approved by user, 2026-09-17):** Build IPIR v0.2 as a new, parallel module at `backend/app/ipir/v0_2/` rather than an in-place breaking rewrite of `backend/app/ipir/package.py`. IPIR v0.1 remains available for backward compatibility during migration. Add an explicit compatibility/migration boundary so the existing deterministic engines (oracle, diff, impact, reconciliation) are reused rather than duplicated for v0.2. IPIR v0.2 is authoritative for the new workbook and REST-connector flows going forward.

**Why:** Lower regression risk against the existing, tested v0.1 pipeline and existing demo/legacy scripts; matches the locked repository structure's `ipir/v0_2/` placement; avoids maintaining two pricing-engine implementations, which the user explicitly ruled out.

**Implementation shape (architectural decisions made while executing D2):**

- **ID strictness reconciliation.** v0.1's identifier pattern (`^[a-zA-Z0-9_.-]+$`, `ipir/common.py`) is permissive; the locked doc requires `^[a-z][a-z0-9_]{1,63}$` for v0.2. Rather than forking every leaf model, v0.2 reuses v0.1's structurally-sound leaf types (`PricingInput`, `PricingConstant`, `RateTable`, `EffectivePeriod`, `NodeReference`, `LiteralValue`) directly, and enforces the stricter ID pattern as a single aggregate validation pass in `IPIRPackageV2`'s package-level validator over every collected ID, rather than duplicating leaf classes solely to change one regex.
- **Expression model.** v0.1's `Expression` is a single flat `operator`+`operands` class; the locked doc requires 8 discriminated-union types. These are new, v0.2-only classes (`backend/app/ipir/v0_2/expressions.py`) tagged with a `kind` discriminator field. v0.1's `Expression` is untouched.
- **Lowering (`backend/app/ipir/v0_2/compat.py::lower_to_v0_1`)** converts an `IPIRPackageV2` into a plain `IPIRPackage` (v0.1) so the *existing, unmodified* oracle evaluator runs it:
  - `LiteralExpression`/`ReferenceExpression`/`TableLookupExpression` map directly to v0.1's `LiteralValue`/`NodeReference`/`NodeReference` (table results are pre-resolved into evaluation context by the existing v0.1 evaluator exactly as they are today; a v0.2 `TableLookupExpression(table_id=X)` therefore lowers to `NodeReference(ref=X)`, which is exactly how v0.1 already exposes table results to calculations).
  - `UnaryExpression("NEGATE")` lowers to `Expression(SUBTRACT, [0, operand])` — v0.1 has no native negate operator; this is a faithful, zero-risk rewrite since v0.1's evaluator is unmodified.
  - `BinaryExpression`/`NaryExpression` map directly to v0.1's `Expression(operator, operands)` for ADD/SUBTRACT/MULTIPLY/DIVIDE/MIN/MAX.
  - `RoundExpression` at the *top level* of a calculation node's expression is hoisted into v0.1's existing `CalculationNode.rounding_rule` (precision=`scale`, mode=`rounding_mode`), which v0.1's evaluator already applies correctly after expression evaluation — this reuses tested v0.1 rounding behavior exactly rather than adding a new evaluator code path. A `RoundExpression` nested anywhere other than the top level is **not supported by this lowering pass** and raises `LoweringNotSupportedError` rather than silently mis-rounding; this is a documented, fail-closed limitation, not a silent gap.
  - `ConditionalExpression` has no v0.1 inline-expression equivalent (v0.1 conditionals exist only as top-level `PricingRule` objects). Lowering synthesizes a `PricingRule` (using v0.1's existing, tested `ComparisonCondition`/`LogicalCondition`/`evaluate_condition`) and substitutes a `NodeReference` to it in the calculation — this reuses v0.1's existing rule-evaluation machinery unchanged rather than teaching the evaluator a new expression type.
  - `on_zero_behavior` on a `DIVIDE` `BinaryExpression` currently only accepts `"REJECT"` (matching v0.1's existing, hardcoded reject-on-zero behavior exactly, so lowering requires no evaluator change). Any other value is rejected at v0.2 model-validation time with a clear "not yet implemented" error — never silently accepted and silently mishandled.
- **Table range/gap/overlap validation.** Added as new, optional, additive fields directly on the *shared* `ipir/tables.py::RateTable`/`TableRow` (`priority: int | None`, `RateTable.requires_total_coverage: bool = False`, `RateTable.default_value: Decimal | None = None`) rather than a v0.2-only duplicate table model — both v0.1 and v0.2 packages get the benefit, and existing v0.1 JSON without these fields is unaffected (defaults preserve current behavior exactly).
- **Outputs.** v0.2's `PricingOutputV2` requires `currency`, `scale`, and `rounding_mode` as non-optional fields (Pydantic enforces presence — no custom validator needed for that half of §6.2). A package-level validator additionally checks that when an output's `source_ref` calculation has a top-level `RoundExpression`, the output's declared `scale`/`rounding_mode` must match it exactly — preventing the published contract and the actual rounding behavior from silently diverging.

## D5 — Controlled Workbook v1 compiler (CP7) implementation shape

**Decision (session 2, 2026-09-17):** Build `backend/app/ingestion/workbook_v1/` as a compiler that parses the locked `RG_*` sheet contract into IPIR v0.2 constructs (`app.ipir.v0_2`) directly, reusing session 1's already-tested semantic validators (`IPIRPackageV2`'s duplicate-ID/cycle/reference/range checks) and the `compat.py` lowering boundary (`run_control_cases`) rather than writing a second pricing evaluator or a second semantic-validation pass. The following implementation-shape choices were made while executing this:

- **Mini-DSL vs raw Excel formulas — scoping.** `RG_CALCULATIONS` rows (`operator` + `operand_1` + `operand_2` + `rounding_mode` + `scale` columns) are RateGuard's own controlled mini-DSL, never Excel formula strings evaluated by Excel or by this compiler. An operand token is one of: a numeric literal (optionally `#`-prefixed, e.g. `#0`), or a lowercase identifier reference to another declared input/constant/table/calculation node (`app.ipir.v0_2.common.ID_PATTERN_V2`). `LOOKUP`'s `operand_1` is a table id. `ROUND`'s `operand_1` is the operand to round; `scale`/`rounding_mode` come from their own columns. `IF`'s `operand_1` is a condition string in a deliberately narrow grammar -- a single `LEFT OP RIGHT` comparison (`OP` in `EQ/NE/LT/LTE/GT/GTE`), optionally joined to exactly one more comparison via a single `AND`/`OR` -- and `operand_2` is `WHEN_TRUE|WHEN_FALSE`. This is narrower than a general boolean-expression grammar (no nested parentheses, no chained ANDs), matching the locked doc's explicit "limited IF" language rather than building more logic than the contract calls for.
- **Defense in depth against raw Excel formulas.** Independent of the mini-DSL, every cell in every required sheet is scanned (`formulas.py::scan_cell_for_unsupported_formula`) for a leading `=` (a live Excel formula string, which openpyxl in formula-preserving/non-`data_only` mode exposes verbatim without evaluating). Any function-name token found that is outside the combined operator/comparison/logical allowlist is rejected as `UNSUPPORTED_WORKBOOK_FUNCTION` with sheet/cell/function detail, matching locked doc section 13.5's exact example and acceptance scenario A8. This is pure text inspection; nothing is ever executed.
- **RG_OUTPUTS has no scale/rounding columns (locked doc section 5.1 lists only `output_id, source_ref, currency`), but IPIR v0.2's `PricingOutputV2` requires them.** Resolved by requiring an output's `source_ref` to name a calculation node whose top-level expression is `ROUND`; the output's `scale`/`rounding_mode` are derived from that node. An output referencing a non-`ROUND` node (or a node that does not exist at all) is rejected as `MISSING_ROUNDING` / `UNRESOLVED_REFERENCE` respectively -- never defaulted.
- **Division-by-zero-path detection is static, not just the existing runtime reject.** A `DIVIDE` calculation whose second operand is a literal `0` is rejected at compile time (`DIVISION_BY_ZERO_PATH`) before the calculation graph is even built, in addition to (not instead of) v0.1's existing unconditional runtime reject-on-zero behavior inherited via the v0.2 model's `on_zero_behavior="REJECT"` default.
- **Structural-defect codes reuse session 1's validator messages via classification, not duplication.** Duplicate IDs, calculation cycles, unresolved references, and ambiguous range overlaps are all still detected by `IPIRPackageV2`'s existing `model_validator` (session 1, CP2) when the workbook-derived package is constructed -- `mapping.py::classify_ipir_validation_error` maps the resulting `ValidationError`'s message text to a specific workbook-compiler error code (`DUPLICATE_ID`, `CALCULATION_CYCLE`, `UNRESOLVED_REFERENCE`, `AMBIGUOUS_RANGE_OVERLAP`, `RANGE_GAP`, `ROUNDING_MISMATCH`) rather than reimplementing those checks a second time for workbook sources.
- **REJECTED vs REVIEW_REQUIRED boundary.** Every check in ZIP/XML safety (macros, VBA, external links, OLE objects, encryption, path traversal, ZIP bombs, entry-count limits), every sheet/column-contract violation, every mini-DSL parse failure, and every `IPIRPackageV2` semantic-validator failure (duplicate IDs, cycles, unresolved references, ambiguous overlaps, missing rounding, currency inconsistency) is a hard `WorkbookRejectionError` -> `REJECTED`, matching the locked doc section 17.1 test list's literal "...rejects" language for every one of those bullets. The only path to `REVIEW_REQUIRED` in this compiler is a structurally valid, successfully-built package that has zero or failing `RG_CONTROL_CASES` rows -- an incompleteness-of-verification problem, not a structural or security defect. `compile_workbook` never raises to its caller; a single `try/except WorkbookRejectionError` at the top of the function is the only place that exception type is ever caught, and it always still returns a `CompilationReceipt` (with the rejection's code/message/details preserved) rather than propagating an exception with no receipt at all.
- **Compression-ratio and entry-count constants (`app/ingestion/workbook_v1/limits.py`), chosen conservatively and documented in-place:** `MAX_ZIP_ENTRIES=2000` (a real 7-required-sheet workbook has well under 100 entries); `MAX_TOTAL_UNCOMPRESSED_BYTES=200 MiB`; `MAX_ENTRY_COMPRESSION_RATIO=100x`, only applied to entries at least `MIN_ENTRY_SIZE_FOR_RATIO_CHECK=1024` bytes uncompressed (so a few bytes of naturally-compressible padding in a legitimate small XML part can't trip it). These are round, conservative numbers chosen to sit comfortably above any legitimate small actuarial workbook's shape and comfortably below what a real ZIP-bomb payload needs to matter; they are not derived from a benchmark corpus (none exists yet for this contract) and should be revisited once one does.
- **Encrypted/password-protected fixture construction.** openpyxl cannot produce a genuinely encrypted `.xlsx` (that requires the proprietary OLE/CFB + ECMA-376 `EncryptionInfo`/`EncryptedPackage` wrapper, which this project deliberately never implements or parses beyond signature detection). The negative fixture (`data/samples/workbook_v1/negative/encrypted_workbook.xlsx`, produced by `generate_workbook_v1_samples.py`) is therefore a minimal, honestly-documented stub: the real 8-byte OLE Compound File Binary signature (`D0 CF 11 E0 A1 B1 1A E1`) that a genuine encrypted OOXML file actually starts with, followed by deterministic zero-padding. This is real, not simulated -- the compiler's check only ever inspects the leading signature bytes (that is genuinely how the encrypted/non-ZIP distinction is made for a real encrypted `.xlsx`), so the fixture exercises the actual code path, not a special-cased test flag. Fabricating a complete, valid OLE sector/FAT/stream structure was judged unnecessary effort for what the check actually verifies, and is recorded here so a reviewer can decide otherwise.
- **A2-scoping judgment call for the "defective workbook" test.** Locked acceptance scenario A2 is "Canonical spec vs defective engine" -- a mission-level, cross-source comparison, not a workbook-compiler concern. `test_defective_workbook_compiles_and_control_case_proves_655` therefore asserts only that the defective workbook is an internally self-consistent, compilable IPIR source whose own embedded control case proves its own declared $655.00 premium (i.e. `VERIFIED` at the compiler level) -- it does not claim $655 is "correct" and performs no comparison against the canonical package. That comparison belongs to the mission-level reconciliation engine (locked doc section 7), which is out of scope for this session.
- **D1 (removing the fabricating `app.adapters.excel`/PDF/PlatformConfig reachable surface) was not executed in this session.** D1's own text says "CP7 must not begin without first executing D1", but the concrete session-2 task list this compiler was built against enumerates 13 specific deliverables scoped entirely to `backend/app/ingestion/workbook_v1/` and does not include touching `app/adapters/*`, `app/agents/supervisor.py`, or any API route. Executing D1 now would mean modifying supervisor/agent/API code with real regression risk, outside what was asked and outside what was tested this session. This is flagged here, unresolved, rather than silently done or silently dropped -- a reviewer should decide whether D1 execution is a follow-up task before `app.adapters.excel`'s fabricated-result behavior is ever exercised through a real mission path.

## D6 — Wire the workbook v1 compiler into the real ingestion boundary; D1's risk was already mitigated at that boundary

**Decision (approved by user, 2026-09-17):** After D5 was implemented, review of the D1 concern found that the actual user-reachable upload path, `PricingSourceIngestionService.register_source` (`backend/app/services/ingestion_service.py`), already rejected `.xlsx`/`.xls`/`.pdf` uploads with `SourceParsingError` *before* any `SourceDescriptor` with `source_type=EXCEL` could ever be constructed -- and `AssuranceSupervisor.compile_source`/`extract_and_compile_source` (where the fabricating `ExcelPricingAdapter` and the Gemini `CHOOSE_EXTRACTION_STRATEGY` decision live) is only reachable via a `SourceDescriptor` that `register_source` produces. There is no other call site. So the fabricating Excel path was already unreachable from the real API for any genuine user upload; it was only exercised by direct internal unit tests of `AssuranceSupervisor`/`ExtractorSpec` in isolation. Given the user's explicit choice of "minimal fail-closed fix now" over full D1 execution, the following narrow, contained change was made instead of touching `agents/supervisor.py` or the Gemini extraction-strategy policy at all:

- `register_source` now accepts `.xlsx` (only `.xlsx` -- not legacy `.xls`) and tags it `SourceFormat.EXCEL` / `ArtifactCategory.SOURCE_WORKBOOK`.
- `compile_source` now branches: `SourceFormat.EXCEL` sources are compiled by a new `_compile_controlled_workbook` helper that calls `app.ingestion.workbook_v1.compile_workbook` directly and lowers a successful `IPIRPackageV2` result to v0.1 via the existing `lower_to_v0_1` boundary, never touching `AssuranceSupervisor` or the legacy `ExcelPricingAdapter`/Gemini extraction-strategy code for this format. A `REJECTED` receipt raises `SourceParsingError` with the receipt's own error codes/messages; `REVIEW_REQUIRED` still returns a package but with `confidence=0.4` and `requires_human_review=True` so it can never be mistaken for a verified compilation. `.xls` and `.pdf` remain rejected exactly as before (message text updated to no longer claim `.xlsx` is unsupported).
- `agents/supervisor.py`, `adapters/excel/adapter.py`, and the Gemini `CHOOSE_EXTRACTION_STRATEGY` decision were **not modified** -- they remain in the codebase, still exercised by their own existing unit tests (`tests/agents/test_extraction_orchestration.py`, `tests/unit/test_adapters.py`), but are now confirmed-by-test unreachable from `PricingSourceIngestionService` for `.xlsx` specifically. PDF still uses the Gemini extraction-strategy path via that same supervisor code, unchanged -- PDF was out of scope for this session per the locked doc's own explicit MVP exclusion (section 4.2).

**Why:** This delivers the substance of the user's chosen option (an actual, reachable, safe path for `.xlsx` that replaces the previously-existing hard rejection, with the fabricating path confirmed unreachable) without the regression risk of editing `agents/supervisor.py`'s working Gemini-decision logic, which full D1 execution would require touching for the PDF path too. Full D1 execution (removing PDF/PLATFORM_CONFIG/the Gemini decision entirely, including from files/tests that don't need to change for the workbook compiler to work) remains open, unresolved follow-up work, tracked here and in STATUS.md -- not silently completed and not silently abandoned.

**Verification:** `tests/agents/test_extraction_orchestration.py::test_ingestion_service_rejects_legacy_xls_and_pdf_uploads` (renamed/narrowed from the prior test, which asserted `.xlsx` was rejected -- that assertion is now the opposite of the intended behavior), `test_ingestion_service_rejects_unsafe_xlsx_workbook` (garbage bytes fail closed via the real compiler, not a fabricated package), and `test_ingestion_service_compiles_canonical_workbook_v1_sample_end_to_end` (the generated canonical sample compiles through the real `register_source` -> `compile_source` path and reaches `VERIFIED`/confidence `1.0`). Full existing suite re-run after this change with zero regressions (see STATUS.md).

## D7 — REST rating-engine connector (CP8) implementation shape

**Decision (session 3, 2026-09-17):** Build `backend/app/connectors/` as the *client* side of the locked doc section 8 REST target-engine connector -- registry, versioned request/response contract, HTTP client with SSRF/timeout/retry controls, and a golden-case health-test function -- entirely on top of session 1's `backend/rating_engine` demo service (the *target* side) and CP7's error-shape convention, without modifying either. The following implementation-shape judgment calls were made while executing this:

- **Registry config shape.** A small, explicit, Pydantic-validated in-memory registry (`app/connectors/registry.py`) built from new `Settings` fields (`app/core/config.py`: `rating_engine_connector_base_url`, `rating_engine_connector_is_local_dev`, `rating_engine_connector_auth_header_name`, `rating_engine_connector_auth_token_env_var`), not a database-backed CRUD admin store. Rationale: the locked doc's own section 18.1 scopes Administration to "minimal connector and threshold display," not full connector management, and that management surface is explicitly a frontend/future-session concern; a Firestore-backed `connectors/{connector_id}` collection (locked doc section 14.1) can be added later without changing `select_connector`'s signature (`connector_id` + `engine_version`, never a URL). Exactly one real entry is registered (`rating-engine-demo`, allowed versions `canonical-v1`/`defective-v1`, mirroring `backend/rating_engine/engines/registry.py`'s own two-version registry exactly). `select_connector` fails closed (typed `UnknownConnectorError`/`UnknownEngineVersionError`, both carrying `ConnectorFailureCategory.NON_RETRYABLE`) for any unregistered connector or undeclared engine version, and never falls back to a default connector -- verified by `tests/connectors/test_registry.py`.
- **Jurisdiction-field reconciliation.** `backend/rating_engine`'s current `QuoteRequest`/`QuoteResponse` (session 1, D3) has no `jurisdiction` field -- its fixture is jurisdiction-fixed (AZ HO3) and adding a field to that model was judged out of scope for this session's narrow client-side task (see "explicitly do NOT modify `backend/rating_engine/*`" in the task scope). The connector's own contract (`app/connectors/contract.py::ConnectorQuoteRequest/ConnectorQuoteResponse`) carries `jurisdiction: str | None` so a caller-supplied value is never silently dropped: `ConnectorClient._to_target_payload` logs it explicitly (`connector_jurisdiction_recorded`, at INFO level, never a secret so no redaction concern) before building the target's wire payload *without* that field (the demo target's `extra="forbid"` `QuoteRequest` would reject an unknown key outright), and `ConnectorClient._parse_response` echoes the caller's original `jurisdiction` back onto the returned `ConnectorQuoteResponse` for the caller's own evidence/traceability use, since the target itself never returns it. `backend/rating_engine/*` was not modified. A future target that natively accepts jurisdiction can be wired to forward it in `_to_target_payload` without any contract change.
- **DNS-rebinding residual limitation (honesty note).** `app/connectors/security.py::resolve_and_validate_host` resolves the destination host itself (`socket.getaddrinfo`, or direct IP-literal parsing) and validates every resolved address against private/loopback/link-local/reserved ranges immediately before each request attempt. This narrows, but does not eliminate, a DNS-rebinding race: the underlying `httpx.AsyncClient` still connects by hostname, not by pinning the specific IP object validated here, so a resolver that changed its answer in the small window between this check and the transport's own `connect()` call would not be caught. A fully rebinding-proof implementation would require a custom `httpx` transport that dials a pre-resolved IP directly while preserving the original `Host` header/SNI -- judged out of scope for this challenge and documented here (and again inline in `security.py`'s module docstring) rather than silently assumed away or overclaimed as complete SSRF immunity.
- **Idempotency "stable response" scoping.** The task's locked doc section 17.1 "duplicate request returns stable response" bullet is honored narrowly: the real `backend/rating_engine` demo target is stateless and deterministic per input (no request-id-keyed store of any kind), so "stable" here means "same inputs + same `request_id` -> same computed `outputs`," verified by `tests/connectors/test_client_golden.py::test_duplicate_request_id_returns_stable_response` sending the identical request twice and asserting equal `outputs`/`engine_version`/`request_id` (not equal `rated_at`, which the target legitimately regenerates per call). No request-id-keyed response cache/store was fabricated on the connector side -- the demo target has no need for one, and building one to simulate a stronger idempotency guarantee than the target actually provides would overclaim what is demonstrated, contrary to the locked doc's own truth-in-advertising standard (section 2).
- **Auth-header design.** `ConnectorRegistryEntry` carries optional `auth_header_name`/`auth_token_env_var` fields; when both are set, `ConnectorClient._do_request` reads the *complete* header value (e.g. `"Bearer <token>"`) from the named environment variable via `os.getenv` at request time and attaches it verbatim -- never a hardcoded value, never placed in a mission payload, never logged unredacted (values are passed through `app/connectors/redact.py::scrub_secrets`, a same-pattern mirror of `app.agents.gemini_client`'s `_SECRET_PATTERNS`/`_scrub_secrets`, before any exception message reaches a log line). The real `backend/rating_engine` demo target enforces no authentication today (documented in its own module docstring, per D3), so this path is exercised only against a purpose-built fake target requiring a bearer header (`tests/connectors/conftest.py::make_auth_required_app`, exercised by `tests/connectors/test_client_negative.py::test_authentication_denied`/`test_authentication_succeeds_with_correct_token`) -- proving the mechanism works end-to-end for a *future* authenticated target without overclaiming that the current demo target requires or exercises it in production.
- **Response-size-limit constant.** `MAX_RESPONSE_BYTES = 1 MiB` (`app/connectors/client.py`), enforced by streaming the response (`httpx.AsyncClient.stream` + `response.aiter_bytes()`) and counting bytes as they arrive, aborting with `CONNECTOR_RESPONSE_TOO_LARGE` the moment the running total exceeds the cap -- never buffering an unbounded body first. Chosen as a conservative, generous constant: a real quote response (a handful of decimal-string outputs plus an optional short trace) is on the order of hundreds of bytes to a few KiB even with a verbose trace; 1 MiB comfortably exceeds any legitimate response shape while still bounding an adversarial/broken target's output, matching the same "conservative, not benchmark-derived" judgment-call style already used for CP7's ZIP-safety constants (see D5).
- **`backend/rating_engine/*` was not modified.** No narrow, documented reason arose to touch it (see the jurisdiction bullet above) -- `backend/tests/rating_engine/` was re-run as part of the full-suite regression below and is unaffected.
- **Scope boundary confirmed by grep.** No file outside `backend/app/connectors/` and `backend/tests/connectors/` imports from `app.connectors` (checked via `grep -rln "app.connectors" app/ tests/` excluding those two directories after this session's changes) -- nothing in `app/agents/supervisor.py`, `app/api/*`, or `app/missions/*` was wired to call the new connector module, matching the task's explicit "integration session is future work" scoping (mirrors D3's own session-1 scoping note).
- **No live route added.** `app/connectors/health.py::test_connector_health` implements the locked doc section 13.2 golden-case health-test *function*, but no `POST /connectors/{connector_id}/test` FastAPI route was added under `app/api/*` this session -- the task scoped this session to the connector module itself, and wiring an actual authenticated admin route is bundled with the same future "integration session" as the rest of the mission-pipeline wiring above.

## D8 — Session 4 (CP9): wiring the Controlled Workbook v1 compiler and REST connector into `AssuranceSupervisor.run_mission`

**Decision (session 4, approved by user via the plan-mode flow, 2026-09-17):** Wire both previously-unwired modules (CP7 workbook compiler, CP8 connector client) into the real mission pipeline by extending `AssuranceSupervisor.run_mission` and `MissionExecutionService.execute_job` in place — no second mission engine, no parallel pipeline. The following implementation-shape judgment calls were made while executing this:

- **`run_mission` gains an orthogonal `target_connector: ConnectorSelection | None` parameter, alongside the existing `right_pkg: IPIRPackage | None`, rather than unifying both onto a single `RatingTarget` abstraction.** The JSON-vs-JSON path's semantic diff, dependency impact, and portfolio blast-radius stages all fundamentally require a real `right_pkg` AST to compare against — a live connector has no AST at all. Forcing both paths through one uniform interface would have required either fabricating a fake AST for the connector case (dishonest) or stripping those capabilities from the JSON path (regression), so the connector path is instead a new, parallel branch inside the same `RISK_DIRECTED_TESTING`/`RECONCILIATION`/`DECISION` stages, writing into the exact same `mismatch_count`/`blocking_reasons` variables the JSON path already uses — never a side channel. Full regression suite confirms zero behavior change to the pre-existing JSON-vs-JSON path.
- **`ConnectorRatingTarget`/`RatingTarget` (the pre-existing, previously-unused abstraction in `app/engines/target/`) was deliberately NOT adopted for this wiring.** It would have required widening the shared `TargetQuoteResult.final_premium: Decimal` (non-optional) to `Decimal | None` across every consumer of that model (`app/engines/reconciliation/`, `app/services/remediation_service.py`), a wider blast radius than this session's connector wiring needed. Instead, the connector branch lives entirely inside `AssuranceSupervisor`'s own `_run_probe`/`_quote_via_connector` closures, returning a plain `Decimal | None`, with an explicit `act_prem is not None and exp_prem == act_prem` guard at every match-comparison site — a connector failure/partial response can never accidentally compare equal to the expected premium and silently pass. `RatingTarget`/`TargetQuoteResult` remain available, unmodified, for a future session that wants to route the connector through the separate `PricingAssuranceRunner` pipeline instead.
- **`asyncio.run()` bridging is safe here, verified by inspection, not assumed.** The full call chain (`worker_endpoint.process_pubsub_assurance_job` → `AssuranceWorker.process_job` → `MissionExecutionService.execute_job` → `AssuranceSupervisor.run_mission`) is entirely synchronous with no already-running event loop, so `ConnectorRatingTarget`-equivalent code (`_quote_via_connector`) can safely call `asyncio.run(self._connector_client_factory().send_quote(...))` inline. The store-level mission lease is acquired before `run_mission` is invoked and held for its entire duration (confirmed in `mission_execution_service.py`), so a synchronous HTTP call inside that window introduces no new duplicate-execution risk — `tests/agents/test_worker_delivery_outcomes.py::test_no_duplicate_execution_under_redelivery_for_connector_backed_mission` proves this directly.
- **Connector-path test-scenario generation reuses the existing `RiskDirectedTestGenerator`/`generate_candidate_scenarios` unchanged**, rather than writing a second test-generation code path: a synthetic, zero-difference self-comparison (`left_pkg` vs itself) is passed into `generate_plan` so the existing boundary/range-generation logic (which derives its scenarios from the package's own declared input ranges/tables, not from the diff list itself) runs exactly as it does for the JSON-vs-JSON path.
  - **Known, documented limitation of the fully automatic path**: `generate_candidate_scenarios`'s baseline "Control Baseline Scenario" derives each input's probe value from that input's own declared `minimum`/`maximum` (midpoint, or whichever bound is present, or `0` if neither). The shipped golden workbook's `roof_age` input declares `minimum=0` and no `maximum` — so the fully automatic path's baseline probe is `roof_age=0`, not the workbook's own embedded golden control case (`roof_age=25`). The mismatch/PASS/BLOCK_DEPLOYMENT decision logic is identical and correct regardless of which value is probed (the oracle and the connector are both evaluating the same package deterministically), but the exact locked dollar figures ($700.00/$655.00) are not guaranteed to appear verbatim from a fully unattended run against an arbitrary workbook whose numeric inputs have an open-ended range. This is flagged here as unresolved follow-up work (a documented UI/API note, or a compiler-level enhancement that seeds `TEST_CANDIDATE_GENERATION` from `RG_CONTROL_CASES` inputs directly, would close this) — not silently worked around. `tests/agents/test_supervisor_connector_path.py` and `tests/integration/test_workbook_to_connector_mission_e2e.py` both prove the exact locked golden figures by seeding the probed scenario with the workbook's own declared control-case inputs (`RiskDirectedTestGenerator.generate_plan` is deterministically overridden to return that one scenario) — this is a legitimate, honest verification of "the independent oracle and the real connector agree/disagree on the declared golden case," not a fabricated pass.
- **First-divergent-node for the connector path** is derived from the mismatched `RuntimeExperiment`'s own `first_divergent_node` field (unset today, so it falls back to the literal `"connector_final_premium"`) rather than a full node-by-node trace diff between the oracle's `PremiumTrace` and the connector's `ConnectorTraceStep` list (the two trace vocabularies are not guaranteed to share node ids one-to-one without a translation layer). This is a scoped, honest simplification: `result.reconciliation.data.root_cause` still names the exact expected/actual values and the connector/engine-version identity, satisfying "identify the exact first divergent node" at the premium-output granularity the connector contract actually provides, but does not currently walk into a shared calculation node deeper than the final premium. Flagged as unresolved follow-up work, not silently narrowed without a note.
- **`StageRecorder`/`MissionStage` (CP2a, previously unwired per D4) is now wired into `run_mission` for every code path** — the 8-stage clean-equivalence fast path, the semantic-diff-blind-spot fast path, and the full 20-stage material-drift path (both JSON-vs-JSON and connector). `COHORT_DISTRIBUTION`, `PIPELINE_IMPACT`, `EXPLANATION_FACTS`, `EXPLANATION_DRAFT` are always recorded `NOT_APPLICABLE` with the reason "not built in this codebase; out of session scope" — confirmed by grep that no implementation module for any of these four exists anywhere in `backend/app/`. `EVIDENCE_FINALIZATION` itself fails (forcing a blocking reason, never a bare PASS) if `StageRecorder.all_accounted_for()` is False at the end of `run_mission` — the concrete enforcement mechanism for "every stage visible... may not silently disappear."
- **Effective-period compatibility** (locked doc section 6.4's "overlapping effective period" compatibility criterion) is newly added to the existing product-line/jurisdiction `review_reasons` check for the JSON-vs-JSON path (an additive `elif` branch). It is honestly NOT evaluated for the connector path — `ConnectorRegistryEntry` carries no declared effective-period/coverage metadata for a live target to compare against, and fabricating one would overclaim what is actually verified.
- **Evidence**: a new `EvidenceType.CONNECTOR_INVOCATION` record is written per connector probe, containing only SHA-256 hashes of the request/response JSON, connector id/engine version, status, and the returned premium — never the raw request/response body, and never a URL or credential. A new, narrowly-scoped `GET /missions/{id}/connector-evidence` endpoint (mirroring the existing Gemini-evidence endpoint's fixed-field-whitelist pattern exactly) serves this; the existing `GET /missions/{id}/evidence` (Gemini-only) endpoint was left untouched, per its own documented "exactly this fixed list" contract.
- **`sources.py`'s workbook-receipt surfacing gap (identified during planning) was fixed**: `compile_pricing_source` now returns `workbook_compilation_receipt` (the real `CompilationReceipt` — compiler_version, artifact_sha256, status, control_case_results, errors — that `_compile_controlled_workbook` already computed and stored in `res.evidence["compilation_receipt"]` but which was previously never returned over HTTP) alongside the pre-existing generic `compilation_receipt` summary (unchanged, still present, so no existing frontend/test consumer of that field is affected).
- **Connector-selection validation happens at mission-create time, not mission-execution time**: `MissionValidationService.validate_mission` now calls `app.connectors.registry.select_connector` for any `source_b.source_type == "API_CONNECTOR"`, converting `UnknownConnectorError`/`UnknownEngineVersionError` into the same structured `ValidationIssue` shape every other validation failure uses. A mission referencing an unregistered connector or undeclared engine version is rejected with 422 before ever reaching the queue — never a mid-execution failure.
- **No new mission engine, no new API framework, no touch to `backend/rating_engine/*`, `app/adapters/*` (PDF/PLATFORM_CONFIG), or the Gemini `CHOOSE_EXTRACTION_STRATEGY` decision.** D1 remains exactly as deferred by D6; this session's scope was strictly the connector/workbook-to-mission wiring, the minimum API surface to drive it (`GET /connectors`, connector-evidence endpoint, workbook-receipt surfacing fix), and the minimum frontend surface (workbook upload + receipt display on `sources/page.tsx`, a connector picker on the same page rather than a separate `missions/new` rebuild, and a Stage Ledger + connector-evidence panel on `missions/[missionId]/page.tsx`).
